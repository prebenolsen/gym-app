# Executive Summary

Top 10 issues ranked by impact
1. CRITICAL: Sensitive secrets (including Supabase service role keys) are committed in repository-level and workspace .env files.
2. CRITICAL: Broken object-level authorization in backend destructive/reorder endpoints allows cross-tenant modification/deletion by guessed IDs.
3. HIGH: Direct dependency vulnerability in axios (high severity advisories) and multiple moderate transitive vulnerabilities in Expo/Express chain.
4. HIGH: Backend N+1 query patterns in history and detail endpoints create severe scalability bottlenecks.
5. HIGH: Mobile app performs API fan-out storms (program->workouts->exercises + 18 monthly history calls) on focused screens.
6. HIGH: No transactional boundaries for multi-step destructive/account operations risks partial data deletion and corruption.
7. HIGH: Active workout session start is race-prone (check-then-insert without DB uniqueness guard).
8. HIGH: Large full-table scans in stats/progress paths due missing user filters and in-memory joins.
9. MEDIUM: Monolithic backend architecture (single ~1900-line file) reduces maintainability and increases regression risk.
10. MEDIUM: Zero automated tests/CI/lint gates; critical user/auth/data flows are unprotected from regressions.

Biggest security risk
- Committed Supabase service role secret + backend using service-role privileged client. If exposed, attacker can bypass RLS and read/write/delete all tenant data.

Biggest performance risk
- Combined server and client N+1 API/database patterns causing multiplicative query growth per user action.

Biggest maintainability risk
- Backend route, business logic, persistence, validation, and error behavior are centralized in one file with weak typing and repeated patterns.

# Critical Findings

[C-01] Secret leakage in repository (.env files contain live credentials)
- Category: Security / Infrastructure
- Severity: Critical
- Impacted code:
  - .env (detected by security string search)
  - backend/.env (detected by security string search)
  - mobile/.env (detected by security string search)
- Why this is dangerous:
  - Service role credentials and anon keys are present in tracked workspace files. Service role credentials grant elevated database/admin capability.
- Attack scenario:
  - Any actor with repository/workspace access can exfiltrate keys, then call Supabase admin/data APIs directly.
- Recommended remediation:
  - Revoke and rotate all exposed keys immediately.
  - Remove secrets from history and enforce secret scanning pre-commit/CI.
  - Keep only .env.example placeholders.

[C-02] Broken object-level authorization in destructive endpoints
- Category: Security / Authorization
- Severity: Critical
- Impacted code:
  - backend/src/index.ts:227
  - backend/src/index.ts:239
  - backend/src/index.ts:242
  - backend/src/index.ts:343
  - backend/src/index.ts:360
  - backend/src/index.ts:365
  - backend/src/index.ts:516
  - backend/src/index.ts:521
- Why this is dangerous:
  - Mutations are performed by foreign-key/id only, without strict user ownership checks in the mutation itself.
  - Backend uses service-role client (bypasses RLS), so missing filters are not protected by DB policies.
- Attack scenario:
  - Attacker guesses another user workout/program UUID and can reorder or delete child records across tenants.
- Recommended remediation:
  - Enforce user_id checks on every update/delete and validate parent ownership before child mutation.
  - Move multi-row operations to SQL RPC with SECURITY DEFINER and strict ownership constraints.
  - Replace service-role for normal user requests with user JWT context where possible.

[C-03] Privileged backend model amplifies authorization mistakes
- Category: Security / Architecture
- Severity: Critical
- Impacted code:
  - backend/src/index.ts:17
  - backend/src/index.ts:18
- Why this is dangerous:
  - Service role key is used for all API requests; any missing WHERE user_id predicate becomes cross-tenant exposure.
- Attack scenario:
  - A single missed filter in any endpoint enables unauthorized data modifications globally.
- Recommended remediation:
  - Use anon key + user JWT for user-level data paths.
  - Reserve service-role client only for explicit admin tasks in isolated code paths.

# High Severity Findings

[H-01] High-risk dependency vulnerabilities (axios + ecosystem advisories)
- Category: Security / Dependency Management
- Severity: High
- Impacted code:
  - mobile/package.json:19 (axios ^1.6.2)
  - npm audit results (root/mobile/backend)
- Why this is dangerous:
  - Known advisories include SSRF/no_proxy bypass and prototype pollution gadgets.
- Attack scenario:
  - Crafted request/response edge cases in vulnerable client libs can bypass expected network protections.
- Recommended remediation:
  - Upgrade axios to >=1.15.2.
  - Upgrade Expo stack to a patched supported line (audit suggests expo 56.x path, evaluate migration impact).
  - Add scheduled dependency audit in CI.

[H-02] Backend N+1 lookups for workout/exercise names
- Category: Performance / Scalability
- Severity: High
- Impacted code:
  - backend/src/index.ts:797
  - backend/src/index.ts:840
  - backend/src/index.ts:893
- Why it is slow:
  - Each session/set triggers additional single-row lookups (workout/exercise name), creating O(N) network round-trips on top of base query.
- Concrete fix:
  - Fetch related names in one query (join/select with foreign relation) or prefetch map by IDs.
- Example:
  - Replace per-session `from('workouts').select('name').eq('id', ...)` with one `in('id', workoutIds)` and map locally.

[H-03] Full-table scan risk due missing user filter on set-history queries
- Category: Database / Performance / Privacy
- Severity: High
- Impacted code:
  - backend/src/index.ts:1100
  - backend/src/index.ts:1178
  - backend/src/index.ts:1103
  - backend/src/index.ts:1194
- Why it is slow:
  - Queries on workout_session_sets do not filter by user_id in initial fetch, then filter in memory via session map.
  - This scales with total table size, not user-specific slice.
- Attack scenario:
  - Large datasets degrade response times and may increase accidental metadata exposure risk in logs/errors.
- Recommended remediation:
  - Add `.eq('user_id', req.userId)` to these set queries.
  - Add composite indexes for frequent predicates.

[H-06] Race condition in active-session start (check-then-insert)
- Category: Reliability / Data Integrity
- Severity: High
- Impacted code:
  - backend/src/index.ts:576
  - backend/src/index.ts:595
  - backend/sql/create-all-tables.sql:85
- Why this is risky:
  - Two concurrent start requests can pass active-session check and both insert active rows.
- Recommended remediation:
  - Add DB partial unique index for one active session per user.
  - Enforce in transaction/RPC.
- Example SQL:
  - `create unique index ux_active_session_per_user on workout_sessions(user_id) where status='active';`

[H-07] Multi-step destructive operations not wrapped in transactions
- Category: Reliability / Consistency
- Severity: High

[M-03] Weak request validation and typing across API surface
- Category: Code Quality / Reliability
- Severity: Medium
- Impacted code:
  - backend/src/index.ts (many req.body assumptions)

- Why this is risky:
  - Invalid payloads fall through to DB errors; compile-time protections are bypassed.
- Recommended remediation:
  - Introduce schema validation (zod/joi) and typed route contracts.
  - Remove `@ts-nocheck` and reduce `any` navigation props.
